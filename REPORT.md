## 5. Acceptance check against published values

These numbers were produced by analyses that predate Infinity-Win (SKA2 on reads; reference mapping after filtering) and are an acceptance check, not a tuning target. Provenance for every pair is in `scripts/expected/`.

### salmonella_trio - Published pairwise SNP distances for the three-isolate Salmonella Heidelberg outbreak set

Source file: `scripts/expected/salmonella_trio.json`
Tolerance: +/- 1 SNP. Infinity-Win compares ASSEMBLIES while the reference numbers come from READS (SKA2) and from a mapping-plus-filtering pipeline. Assembly errors, repeat collapsing, and differences in filtering move a 0-2 SNP distance by one or two counts without any of the methods being wrong. A discrepancy of exactly +/-1 SNP is therefore accepted and still printed; anything larger fails. make_report.py prints expected, observed and the difference for every pair, so a near-miss is never hidden.

Two bases are reported. **As reported** is the engine's own `cluster_<id>.dist.tsv`, which is authoritative. **Filtered** is Recomputed from variants, pivot contigs >= 5 kb only (pivot contigs >= 5000 bp), recomputed from `cluster_<id>.variants.tsv` by the benchmark scripts. It exists because Infinity-Win deliberately does not filter (section 2 lists no filtering among its goals; section 15 says repeats are flagged, not corrected) while every published reference number here *is* filtered - so the unfiltered comparison is not apples to apples.

> This is a recomputation by the benchmark scripts, not an engine output. It counts positions where two members' alleles differ and does NOT apply the comparable-coverage restriction of section 6.9, so its unfiltered value can exceed the engine's own. Treat it as evidence about the filter, never as a replacement for the engine's distance.

## 6. Switch invariance: do the switches change the answer?

PROJECT.md section 10.2 property 6 requires that flat mode, hierarchical mode and every cache switch give **identical** variants, distances and trees: each switch removes work, not accuracy. This compares every configuration's pairwise SNP counts *and* its variant lists with the baseline's. A switch that is faster but wrong has not been shown to pay, so a difference is classified rather than quietly averaged away:

| classification | meaning |
|---|---|
| identical | reproduced the baseline exactly |
| **DEFECT** | differs, and nothing in DECISIONS.md says it may (`flat`, `no_piece_cache`, `no_profile_grouping`) |
| documented deviation (D16) | `no_block_skip` changed distances while its variant list stayed identical - exactly what DECISIONS.md D16 records |
| **UNDOCUMENTED** | `no_block_skip` changed the *variants* too, which D16 says must stay identical |
| expected (different pivot) | `single_cluster` compares every genome to one pivot, so its pair set and coordinates differ by construction |

> **6 configuration/dataset combination(s) differ from the baseline with no documented reason.** Section 10.2 property 6 is not satisfied, so the timing differences in section 3 cannot be read as pure optimisation gains until this is fixed.

## 11. How to reproduce

```bash
export PATH="$HOME/.cargo/bin:$PATH"
cargo build --release                     # binaries land in /tmp/infinity-target/release

scripts/real_datasets.py --datasets all   # copy + verify the real datasets
scripts/run_matrix.py --dry-run           # show every command line first
scripts/run_matrix.py                     # 6 configurations x every dataset
scripts/baselines.py all --dataset ncbi_pd_cluster \
    --run-dir bench-work/matrix/ncbi_pd_cluster/baseline
scripts/make_report.py                    # writes REPORT.md
```

The matrix command lines actually used are stored per cell in `bench-work/matrix/summary.json` under `cells[].run_command` and `cells[].bench_command`, so any single cell can be re-run by hand.
